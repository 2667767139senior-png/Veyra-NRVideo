# AFG — 自适应固定帧率补帧（2026-11-26）

状态：实现完成，单元测试与网格仿真通过；**真机 VFG 位置验证待跑**（见第 8 节）。
本文取代 `docs/FIXED_TARGET_FG_2026-11-25.md` 里"按间隔算帧数、倍率随对变化"的设计。

## 1. 为什么要重做

2026-11-25 的实现把"固定目标帧率"落成了**每对算一个整数倍率**：
`count = round(span × targetFps / 1000)`，生成帧落在 `t = i/(count+1)`。

两个后果，都是设计层面的：

1. **位置不是目标位置**。30fps 源、50 目标、33.3ms 间隔，需要的是 20ms 处一帧
   （`t=0.6`），而 `i/(count+1)` 只能给出 16.7ms（`t=0.5`）。输出间隔只能在
   16.7 / 33.3 ms 之间跳，平均是 50，节奏不是。
2. **平均正确 ≠ 节奏正确**。这正是本项目明确拒绝的验收方式。

AFG 改成：**先有输出网格，再决定每个网格点由谁填充**。

## 2. 输出网格

```
period = 10 000 000 / targetFps          [100 ns]
slot(n) = origin + round(n × period)     [源时钟 100 ns]
```

- `origin` 是本次运行**第一个真实帧**的时间戳。网格从画面开始的地方开始，
  所以永远不会有"过去的槽位"。
- 每一对真实帧 `(a, b)`：
  - `slotB = ceil((b − origin)/period)` —— `b` 之后（含）的第一个槽位；
  - `(lastSlot, slotB)` 之间的每个槽位都生成一帧，位置 `t = (slot − a)/(b − a)`；
  - 真实帧占用 `slotB`。
- 槽位时间**每次从 origin 重算**，不做累加，所以长时间运行不漂移（单测跑 5 分钟
  29.97→50，全部槽位仍是周期的整数倍）。

### 2.1 时间戳的含义

| 时间 | 用途 |
|---|---|
| `a100ns` / `b100ns` | 真实内容时间，只用于算 `t` 和 VFG 的 A/B 对 |
| `slot(n)` | **呈现时间**，写进 `BatchFrame::pts100ns` |
| `realPts100ns` | 真实帧的呈现时间（= 它占的槽位） |

`PresentationScheduler::deadline(pts) = host + (pts − source) + delay` 是一条线性
媒体时钟，所以只要 PTS 在网格上，Present 时刻就在网格上。**Presenter 不需要改**——
这一点是审计过的，不是假设：实时路径对 batch 内每一帧（真实帧与生成帧一视同仁）
都等待 `timeline.deadline(item.pts100ns)`，过期帧丢弃。

### 2.2 两种节奏策略

| 策略 | 行为 | 代价 |
|---|---|---|
| `Fixed`（默认） | 真实帧取"不早于自己时间戳"的第一个槽位 | 最多一个周期的延迟（50 目标 = 20 ms） |
| `Latency` | 真实帧保持原时间戳，只填空隙 | 不加延迟，但输出是两套时钟的并集，间隔不完全均匀 |

真实帧**永远不会被提前**：`slotB` 的定义就是 `≥ b`。

## 3. 显式 Timestep：先验证，再依赖

AFG 的位置只有 VFG 的 `Timestep` 能表达。这条能力在此前的代码里存在，
但**从未被任何管线调用过**（`generate()` 的 timestep 参数恒为 0），所以不能当成已知。

已用真实 SDK 运行时（`NVVideoEffects.dll` 1.3.0，直接调 `NvVFX_*`）确认：

| 事实 | 结果 |
|---|---|
| `NvVFX_SetF32` 是否导出 | 是 |
| `Timestep` 是否为真实参数（F32） | 是；按 U32 读返回参数类型错误 |
| 取值范围 | 严格开区间 `(0,1)`：`0.0`、`1.0`、`-0.5`、`1.5` 全部拒绝 |
| 与 `FrameMultiplier` 的关系 | **互斥**：`FrameMultiplier≥2` 时写 `Timestep` 被拒绝；写回 0 后可写 |
| 同一对连续写不同 Timestep | 可以（0.2/0.4/0.6/0.8/0.35/0.65 依次接受） |
| 本机 `NvVFX_Load` | 失败（RTX 3080 = SM 8.6，非 VFG 原生架构） |

因此代码做了两件事：

1. `VfgBackend::timestepAvailable()`（→ `EnhanceGraph::vfgTimestepAvailable()`）
   在初始化后如实报告；
2. `EngineController` 的 AFG 准入条件包含它。**没有 Timestep 就不进 AFG**——
   否则会用 `i/M` 的位置去冒充网格时间，得到"帧率对了、画面在抖"的伪结果。

「Run 是否真的把帧放在那个位置」只能靠 GPU 像素验证，工具已就绪：
`tests/integration/VfgTimestepProbe.cpp`（CI 产出 `veyra-vfg-timestep-probe` 产物）。
它让一个红色方块在 A/B 之间移动固定距离，测量每个生成帧的质心与
`A + t(B−A)` 的偏差，先跑倍率模式做对照，再跑六个 Timestep。

## 3.5 前瞻：实机跑出来的第一个真问题（2026-11-26）

第一次实机（RTX 3080 Laptop，2560×1440，30 fps 源，目标 50，44 秒）的日志：

```
afg-output samples=256 intervalMs p50=19.93 p95=27.06 p99=27.14 mean=20.00 sd=4.30
fixed-target mode=afg contentFps=30.00 frames=0 generatedFps=19.35 fgGpuP95Ms=17.340 loadCap=1
```

均值 20.00 ms 完全正确，`generatedFps` 也对——**但 p95 是 27 ms**。分布是两个峰：
19.9 与 27.1。原因不是 GPU 慢，而是**时序上不可能**：槽位 20 ms 的那一帧要用 A、B
两个真实帧插出来，B 要到 33.3 ms 才存在。没有前瞻时，Presenter 只能在这一帧"能算出来"
的那一刻（媒体时间已越过它的槽位）把它显示出去，于是间隔变成 27/13 交替——
**均值对、节奏错，正是本模式要消灭的那东西**。

修法：给整条输出时间轴加一个**固定前瞻** `guard100ns`，取"一个输入间隔向上取整到
整数个输出周期"（30→50 得 2 个周期 = 40 ms，夹在 1~3 个周期之间）。它加在每一帧上，
所以间隔不变、只整体后移：

- 生成帧在 `slot + guard` 到期，此时 B 早已到达，还有 ≥ 一个周期的余量；
- 真实帧同样 +guard，顺序与间隔都不变；
- 只对"固定网格"生效；"低延迟"保持源时钟、不加前瞻（按设计接受间隔不均匀）。

代价是 40 ms 延迟，必须在产品里说出来，而不是藏起来：面板的节奏说明直接写明，
日志加了 `guardMs` 字段，状态块单独一行"前瞻 40.0 ms（2 个输出周期）"。

### 3.6 前瞻必须闭环：固定值仍然漏槽（2026-11-26，同日第二次实机）

加上固定前瞻后重跑（720p30 → 50，42 秒），27/13 **没有消失**：

```
afg-output p50=19.95 p95=27.11 p99=27.23 mean=20.00 sd=4.19 offCadence=102/256
guardMs=40.000    ← 也就是 26.7 ms 的提前量
player-timing     gpuReadyP95Ms=24.797 gpuFgBatchP95Ms=23.887
```

26.7 ms 的余量对上 24.8 ms 的流水线时延，**只差 2.7 ms**，于是每三个批次漏一次、
每次漏 7 ms——均值仍然是 20.00，p95 是 27。算术上可以复现：`guard + period − span`
= 40 + 20 − 33.3 = 26.7。

结论：输入间隔只能定出前瞻的**基准**（一个间隔换半个批次的存在性），定不出足够量。
VFG 的单帧耗时在同一块卡、同一分钟内实测 4.4 ~ 30.1 ms，**任何写死的常数都会要么不够、
要么永久过大**。

所以前瞻改成闭环，被调节量是"已经送进 Present 的帧相对自己槽位晚到多少"
（`AfgLateness`，按生成帧/真实帧分别统计 P95）：

| 观测 | 动作 | 边界 |
|---|---|---|
| 任一 P95 > 1 ms | 周期数 += `ceil(P95 / 周期)`，每次窗口最多 +2 | 总周期数 ≤ 6（50 FPS 下 120 ms） |
| 连续 4 个窗口 P95 ≤ 1 ms | 周期数 −1 | 不会低于基准（2 个周期） |
| 每次变化 | 写 `afg-guard` 日志，记录变化前后的周期数与晚到 P95 | 变化只影响相邻一次间隔，不累积 |

它调节的是**症状**而不是对流水线建模：GPU、驱动、源帧率、场景任何一个变了，这个循环
都还成立。每次变化会把整条输出后移整数个周期，跨一次间隔，然后重新稳定；
`FixedTargetScheduler::reset()` 保留已学到的周期数，所以设备/帧重置不会让它从头爬。

面板与日志同步：`fixed-target` 行加了 `guardPeriods` / `guardExtra` /
`lateGenP95Ms` / `lateRealP95Ms`，`afg-output` 行加了间隔直方图（`tail=18-20ms=150 26-28ms=51`），
报告脚本把"稳态晚到 P95 > 1 ms"直接判 FAIL——**因为均值 20.00 而 P95 27 的那种输出，
就是要被拦下的那种"看起来对"的结果**。

## 4. 调度规则

| 情况 | 行为 | 理由 |
|---|---|---|
| 模式关闭 / 目标 0 | 旁路，`reason=off` / `targetOff` | 面板允许 0–160 |
| `span ≤ 0` | 旁路 | 时间戳乱序 |
| `span > maxIntervalMs`（默认 100 ms） | 旁路 + **重新锚定** | 停顿不插帧，也不补偿 |
| 源帧率 ≥ 目标×0.98 | 旁路 | 已达标，插帧只是复制 B |
| 单对超过 `maxRuns` | 丢最早的槽位，计数 `droppedCap` | GPU 跟不上时丢帧，不欠账 |
| 槽位落在端点上（t≤0 或 ≥1） | 丢弃并计数 `droppedNear` | 没有可插值区间 |
| 槽位离端点 <0.5% | 把 `t` 钳到 0.5% / 99.5% | 0.2 ms 的位置误差看不见，节奏的洞看得见 |

`maxRuns = clamp(ceil(targetFps/25), 2, 7)`：按"最慢的 25 fps 内容"算需要几帧。
50 → 2、80 → 4、144 → 6、160 → 7（VFG 组宽上限 8）。

**已知上限**：源 20 fps（50 ms）配 144 目标需要 7.2 帧/对，超过 7 的槽位池，
会持续丢槽（`droppedCap` 增长、`offCadence` 上升）。20 fps 内容请把目标放在 140 以内。

## 5. 与旧模式的关系

- 倍率模式（Legacy）**代码路径未改**：不经过 `FixedTargetScheduler`，
  `fixedTargetCapacity(off, m) == m`，图与 VFG 池的尺寸与改动前完全一致。
- 两种模式互斥：面板选其一时隐藏另一方的控件。
- 切换/重置/seek 时 `fixedTarget.reset()` + `afgPace.reset()`，
  网格与统计都从头开始，不继承上一模式的时间戳或缓冲。

## 6. 顺带修掉的缺陷

1. `EnhancementSettings::activeVideoSettings()` 用**原始** `multiplier<=1` 清空
   `fgFixedTarget`。固定目标模式隐藏倍率控件，所以这条规则会在用户看不见的地方
   把模式关掉。现在只在"后端不是 VFG"时清空。
2. `FixedTargetConfig::maxRuns` 的结构体默认值与 UI 派生值不一致；
   现在两者都由 `fixedTargetRunsFor()` 决定。
3. 删除了上一版遗留的 `tools/fixed_target_sim.py`（它建模的是被否定的
   "按间隔算整数倍率"算法），由 `tools/afg_grid_sim.py` 取代。

## 7. 遥测

每秒一行，字段与代码一一对应：

```
fixed-target mode=afg targetFps=50.00 cadence=fixed buffer=balanced contentFps=29.41
  sourceMs=34.000 periodMs=20.000 frames=1 timestep[1/1]=0.600@2000.000ms
  realSlotMs=2033.333 snapMs=13.333 generatedFps=19.86 fgGpuP95Ms=6.120 loadCap=3
  bypass=0 reason=grid intervals=310 generated=205 droppedCap=0 droppedNear=0
  droppedLoad=0 loadLimitedPairs=0 resyncs=1 bypassLong=0 bypassAtTarget=0 bypassOff=0
afg-output targetFps=50 samples=256 intervalMs p50=20.01 p95=20.34 p99=21.90
  mean=20.02 sd=0.31 offCadence=2
```

`afg-output` 是在 **Present 成功返回后**采样的间隔分布，`offCadence` 统计偏离
`1000/targetFps` 超过 10% 的间隔数——这是"均匀"与"平均对"的区别所在。
`generatedFps` 是两个日志点之间**实测**插入速率（生成数 / 源时钟增量），不是目标值；
`fgGpuP95Ms` 是 VFG 单次 Run 的 Fg1 阶段 P95；`loadCap` 是它换算出的每对可承受帧数。

`fixed-target` 行另有三个"闭环证据"字段，是判定均匀性的第一手数据：

| 字段 | 含义 |
|---|---|
| `guardMs` / `guardPeriods` / `guardExtra` | 前瞻总量、折合周期数、其中由测量加上去的部分（见 §3.6） |
| `lateGenP95Ms` / `lateRealP95Ms` | 上一窗口内生成帧/真实帧相对**自己槽位**晚到多少（P95，ms）；持续 >1 ms 就等于漏槽 |
| `afg-output` 的 `tail=` | 间隔直方图（2 ms 分桶），27/13 交替在这里是两个峰而不是一个均值 |

## 7.1 面板上的设置与状态（没有装饰性开关）

| 设置 | 真正改的是什么 |
|---|---|
| 目标帧率 0–160 | `1000/targetFps` 的输出槽位间隔；0 = 不插入 |
| 输出节奏 | 真实帧是否被搬到网格上（最多 +1 个周期延迟）还是只填空隙（零延迟、间隔不均） |
| 缓冲策略 | `maxIntervalMs`（60/100/250 ms 判为停顿）与每对帧数上限（紧凑固定 2，平衡/宽松按目标帧率导出 ≤7） |
| GPU 负载自适应 | 用实测 VFG 单帧耗时算出每对负担得起的帧数；**只下调**，被删的槽位计入 `droppedLoad` |
| 回退策略 | Timestep 生成失败时，同一对按普通 2 倍位置重试一次并保留网格时间戳（日志 `target=timestep-fallback`），或直接按补帧失败处理 |

状态块显示的是三组互相独立的测量值，加上调度器自己的计数：

```
目标 50 FPS · 输出节奏 固定网格（真实帧最多晚 13.3 ms，另加前瞻 60.0 ms）
源（实测）29.8 · 生成 19.9 · 提交 49.7 FPS
提交间隔 P50 20.02 · P95 20.34 · P99 21.90 ms · 偏离 2/256
前瞻 60.0 ms（3 个输出周期，其中自适应 1）：生成帧要等第二个真实帧才能存在，这段延迟买的是均匀间隔
晚到 P95 生成 0.42 · 真实 0.18 ms（相对各自的槽位；持续 >1 ms 说明这一路在漏槽）
丢槽 上限 0 · 过近 0 · GPU 0 · 重锚定 1
VFG 6.12 ms/帧 · 目标周期 20.0 ms · 旁路 长间隔 0 / 已达目标 0
```

面板**刻意没有**"显示帧率"这一项：我们能测的只有自己提交的间隔，屏幕实际扫出多少帧
在进程内不可观测。所以只写"提交"，不写"显示"。模式选中但跑不起来时，状态块第一行
直接给出门禁原因（补帧关闭 / 后端不是 VFG / 图片源 / 呈现端自带补帧 /
运行库没有 Timestep 参数 / 等待第二帧）。

## 7.2 异常场景与恢复策略

| 场景 | 行为 |
|---|---|
| 稳定 30 fps | 每 3 对生成 2 帧（t = 0.6 / 0.2+0.8 / 0.4），输出恒定 20 ms |
| 稳定 25 fps | 每对 1 帧 t = 0.5，真实帧 40 ms 已落在网格上，无延迟 |
| 25–30 波动 | 每对帧数按间隔变（0 或 1），输出间隔仍是 20 ms |
| 源降到 20 fps | 每对 2 帧，输出仍 20 ms；超过 `maxRuns` 的槽位计入 `droppedCap` |
| 采集卡卡顿（> 阈值） | 该对旁路（`reason=longInterval`），网格重新锚定，**不补欠账** |
| 暂停后恢复 | 间隔超阈值 → 旁路重锚；`resyncs` +1 |
| 时间戳异常（b ≤ a） | 旁路（`reason=interval`），不产生计划 |
| 重复帧 | 交给既有 `ContentDedup`/`pacingRepair`；调度器只按时间戳工作 |
| VFG 耗时突增 | `loadCap` 下调 → 少生成、计入 `droppedLoad`，延迟不增长 |
| GPU 满载 | 同上；关闭自适应则表现为 `offCadence`/P99 恶化，日志可见 |
| VFG 调用失败 | 回退策略开：同对 2X 重试一次；关：`FailedBackend::Fg` 走既有恢复 |
| 超截止时间 | 准入用网格槽位算截止（`firstPts`/`lastGenerated`），过期的生成帧由 Presenter 丢弃 |
| 队列堆积 | 每对计划有上界（`maxRuns`/`loadCap`/7），丢弃"最新"槽位，无跨对累积 |
| 刷新率不匹配 | 输出网格与刷新率无关；Presenter 的 Even Presentation/VSync 抖动自适应继续生效 |
| 模式切换 | `fixedTarget.reset()` + `afgPace.reset()`，网格与统计清零 |
| 重启 | 设置全部持久化（`fgFixedTarget*` 5 个键），旧配置无这些键时取默认值 |
| 设备重置 | `hardFrameReset` 时同样 reset，重锚定到重置后第一帧 |
| 长时间运行 | 槽位每次从 origin 重算（不累加），5 分钟 29.97→50 单测零漂移 |

## 9. 一句话

AFG 的正确性不再依赖"平均帧率"：槽位在时间轴上是确定的，生成位置由 VFG 的
Timestep 指定，真实帧只会延后到网格上。若 GPU 或 SDK 做不到，日志里的
`reason` / `droppedCap` / `droppedLoad` / `offCadence` 会直接说出来，
而不是让计数器显示 50。
